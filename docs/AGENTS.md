# 独立开发者代运营 Agent

## 文档读取规则

接到任务后，优先读取项目 `./docs` 目录下已经存在的产品与开发文档：

- `SDD-独立开发者代运营Agent.md`：当前产品范围、业务流程、架构、数据模型、API、里程碑与验收标准的最高依据。
- `SPEC.md`：如存在，补充读取项目目标、功能范围、技术栈选型。
- `ARCHITECTURE.md`：如存在，补充读取系统分层、领域模型、目录结构、模块边界。
- `DEV_PLAN.md`：如存在，补充读取开发阶段、迭代顺序、当前所处阶段。
- `CHECKLIST.md`：如存在，补充读取各阶段验收清单。

严格遵守 SDD 中已经确认的产品范围、架构原则、数据模型、API 契约和里程碑计划。
**不允许擅自推翻已确认的架构或产品决策；如发现文档冲突，先说明冲突点并等待人工确认。**

## 项目目标（最终愿景）

构建一个面向独立开发者与一人公司的代运营效率工具。开发者专注产品与代码，运营者使用本系统理解客户产品、制定运营策略、生成多平台内容、完成人工审核与发布，并持续追踪效果。

最终产品具备：

- 客户与产品信息管理：管理多个独立开发者客户及其产品资料。
- 产品理解引擎：基于产品输入生成结构化产品画像，包括定位、目标用户、卖点、内容主题和语气风格。
- 运营策略生成：为国内、海外或混合市场生成平台选择、内容矩阵、发布节奏和增长策略。
- 运营计划排期：按周或按月生成内容日历，并支持人工调整。
- 多模态内容生成：生成文字、图文和视频内容，支持一个核心主题适配多个平台。
- 审核工作流：所有内容必须经过人工审核后进入发布流程。
- 发布组件：优先支持 X/Twitter、掘金等 API 发布；其他平台允许半自动发布。
- 数据追踪与优化：手动录入效果数据，生成简单报表，并为后续策略优化提供依据。

## 当前阶段（MVP）

第一版是单运营者使用的内部 Web 工具，技术栈为 Python 后端 + Next.js 前端 + SQLite。当前执行节奏以 `docs/DEV_PLAN.md` 为准：M1 交付可用 MVP 闭环，M2/M3 再优化内容质量和生产效率。

M1 MVP 要走通“客户建档 → 产品画像 → 策略方向 → 一周排期 → 文字内容生成 → 人工审核 → 复制或导出用于人工发布”。M1 不做 SaaS 化，不做客户自助门户，不做多运营者协作，不做移动端，不接入真实平台发布，不做效果数据报表。

## 开发任务执行前置约束

1. 接到开发任务，**先输出规划：目标、变更文件列表、实现方案、风险点**，等待人工确认批准之后，再开始写代码。
2. 坚持外科式修改，禁止无理由大范围重构现有代码；一次只解决一个明确任务。
3. 禁止一次性实现整个产品，必须按 SDD 的里程碑拆成垂直切片小步迭代。
4. 涉及数据模型变更、API 契约变更、架构分层变更、第三方服务接入、发布平台策略变更时，必须等待人工批准。
5. 不得绕过人工审核流程直接实现“生成即发布”的能力。

## 通用编码纪律

- Python 代码必须使用类型标注；Pydantic schema、SQLAlchemy model 和 service 返回值保持清晰边界。
- TypeScript 使用严格模式，禁止 `any`；前端组件必须声明 Props 类型。
- 所有 IO、数据库、网络和第三方 API 调用必须捕获异常，设置合理超时，禁止吞异常。
- 数据库写操作必须考虑事务边界，失败时不得留下不一致状态。
- 敏感信息禁止硬编码，密钥、API Key、Cookie、平台凭证走环境变量或加密存储。
- 新增依赖必须说明理由，不引入非必要重型依赖。
- 状态管理遵循单一数据源原则，不允许组件间通过全局变量通信。
- 修改完成后做自我评审：检查边界 case、异常处理、安全风险、数据一致性和文档一致性。

## 人与 Agent 的协作

项目负责人负责：

- 产品范围和优先级
- 架构决策和技术选型
- 数据模型和 API 契约
- 第三方服务选型（LLM、图像生成、视频生成、平台 API 等）
- 内容发布策略和平台优先级
- 是否允许进入下一里程碑
- 是否允许发布真实客户内容

开发 Agent 负责：

- 探索代码、依赖和现有实现
- 编写代码和测试
- 执行本地验证
- 维护文档与代码一致性
- 报告不确定性、失败原因和剩余风险
- 在不扩大范围的前提下完成当前垂直切片

开发 Agent 不得自行扩大任务范围，也不得擅自改变产品策略、审核策略或平台发布策略。

## 开发流程

每个任务都必须遵循以下步骤：

1. 说明当前目标和任务范围。
2. 阅读相关文档、入口、模块、调用方、测试和依赖。
3. 提出实现方案。
4. 如涉及架构、数据模型、API 契约、第三方服务、发布平台或安全策略，等待人工批准。
5. 实现一个垂直切片。
6. 立即执行聚焦验证。
7. 检查代码 Diff。
8. 记录结果、风险和下一步。

禁止一次性实现整个产品。

## MVP 范围

M1 MVP 只支持：

- 客户管理：客户增删改查、产品基础信息录入、客户状态管理。
- 产品理解：基于客户产品信息生成产品画像，并支持人工编辑。
- 运营策略方向：基于产品画像生成足够支撑一周排期的策略，并支持人工调整。
- 一周内容排期：以列表视图为主，支持日期、平台、主题、内容形式和状态调整。
- 文字内容生成：基于排期项生成标题、正文和标签；图文、视频和更强的一鱼多吃放到 M2/M3 优化。
- 审核工作流：待审核列表、通过、修改后通过、拒绝、延后。
- 人工发布准备：审核通过内容可复制或导出为 Markdown/JSON，由运营者人工发布。
- 本地优先存储：SQLite 数据库，本地运行，不要求高并发和分布式架构。

第一版不实现：

- SaaS 化、租户体系、付费系统
- 客户自助门户
- 多运营者协作和复杂权限系统
- 移动端
- 真实平台凭证管理
- 自动发布和发布记录
- 效果数据录入和报表
- 所有平台全自动发布
- 自动抓取所有平台数据
- 自动克隆 Git 仓库并分析代码
- 真人出镜视频和复杂剪辑
- 未经审核的全自动发布

只有当前功能经过验证后，才能逐步增加新能力。

## 架构边界

保持以下职责分离：

### 后端（Python / FastAPI）

- `backend/app/main.py`：FastAPI 应用入口。
- `backend/app/config.py`：配置读取，禁止硬编码密钥。
- `backend/app/database.py`：数据库连接与会话管理。
- `backend/app/models/`：SQLAlchemy 数据模型。
- `backend/app/schemas/`：Pydantic 请求和响应模型。
- `backend/app/api/`：API 路由，保持薄控制器，只做参数接收、鉴权预留和响应组织。
- `backend/app/services/`：业务逻辑，包括产品理解、策略生成、内容生成、审核、发布调度和数据统计。
- `backend/app/adapters/`：平台适配器，封装 X/Twitter、掘金、小红书、Reddit 等平台差异。
- `backend/app/utils/`：通用工具函数。
- `backend/tests/`：后端测试。

### 前端（Next.js）

- `frontend/src/app/`：App Router 页面。
- `frontend/src/components/`：可复用 UI 组件。
- `frontend/src/lib/`：API 调用、格式化、客户端工具。
- `frontend/src/types/`：前端类型定义；必须与后端 schema 保持一致。
- `frontend/src/styles/`：样式与设计变量。

### 脚本与文档

- `scripts/`：数据库初始化、备份、维护脚本。
- `docs/`：SDD、开发约束、验收清单和架构记录。

平台适配器必须插件化。新增平台时应新增适配器或配置，不得把平台特殊逻辑散落到核心业务服务、页面组件或数据库操作中。

## 数据模型契约

核心实体及其关系必须与 SDD 保持一致，并在后端模型、后端 schema、前端类型和 API 文档之间同步：

- `Client`：购买代运营服务的独立开发者客户。
- `ProductProfile`：AI 生成并经人工修订的产品运营画像。
- `Strategy`：基于产品画像生成的运营策略。
- `Plan` / `ScheduleItem`：运营计划和具体内容排期项。
- `ContentItem`：一条待生成、已生成、待审核、已审核或已发布的内容。
- `ContentVersion`：内容版本记录，用于重新生成和历史追溯。
- `PlatformCredential`：客户的平台发布凭证，必须安全存储。
- `PublishRecord`：发布结果记录，包括状态、链接、错误原因和重试信息。
- `ContentStats`：内容效果数据，包括曝光、点击、互动和转化指标。

涉及数据模型变更时，必须：

1. 更新数据库模型和迁移策略。
2. 更新 Pydantic schema。
3. 更新前端 TypeScript 类型。
4. 检查所有引用该模型的 API、服务、页面和测试。
5. 说明已有数据如何迁移或兼容。
6. 等待人工批准。

禁止在未更新契约的情况下，在某一层私自扩展字段。

## API 契约

- API 路径、请求体、响应体和错误格式以 SDD 的「API 设计」为准。
- API 返回必须结构化，禁止返回只有字符串的临时响应。
- 错误响应必须包含可定位的错误信息，便于前端展示和日志排查。
- 与 LLM、图像生成、视频生成和平台发布相关的外部调用必须经 service 层封装，不允许页面或路由直接调用外部服务。
- 所有新增 API 必须能在 Swagger 或等价文档中被识别。

## 前端 UI 规范

- 产品应是运营者高频使用的内部工作台，界面应安静、清晰、利于扫描和批量处理。
- 页面优先服务真实工作流：客户列表、客户详情、产品画像、策略、排期、内容生成、内容审核、复制导出；发布记录和数据报表属于后续阶段。
- 不做营销式落地页，不用夸张 hero 区，不把核心工作流藏在介绍页之后。
- 表单必须有校验和错误提示，不允许静默提交失败。
- 加载状态、空状态、失败状态和保存成功状态必须有明确 UI 反馈。
- 内容列表、审核队列、发布记录和报表必须支持清晰的状态展示。
- 颜色、间距、字号优先使用设计变量或统一样式约定，避免散落硬编码。

## AI 与多模态生成约束

- LLM 调用必须封装在后端服务中，Prompt 模板应集中维护，避免散落在路由或前端组件。
- AI 输出必须尽量结构化，并在保存前做 schema 校验。
- 产品画像、运营策略、内容排期和内容生成结果都必须允许人工编辑。
- 图像生成和视频生成必须记录生成参数、状态、失败原因和产物地址。
- AI 生成内容不得默认直接进入发布状态，必须进入审核队列。
- 调用失败、限流、超时和成本风险必须可见，不得静默重试掩盖问题。
- 不得把客户敏感产品信息发送给未授权的第三方服务。

## 审核与发布规则

- 所有内容必须经过人工审核后才能发布。
- 审核状态流转必须明确，禁止跳过必要状态。
- 审核操作至少支持：通过、修改后通过、拒绝、延后。
- 发布队列只能消费审核通过的内容。
- 自动发布必须记录 `PublishRecord`，包括平台、内容、发布时间、状态、发布链接、失败原因和重试次数。
- 发布失败必须允许人工查看原因，并按 SDD 规则决定是否重试。
- 半自动发布应提供复制内容、打开平台发布页、记录人工发布结果的能力。
- 不得为了演示方便而绕过凭证校验、审核状态或发布记录。

## 安全规则

- 客户产品信息、运营策略、内容数据和平台凭证均视为敏感信息。
- API Key、Cookie、账号密码和平台凭证必须加密存储或走环境变量，禁止提交到代码仓库。
- `.env` 文件必须加入 `.gitignore`。
- 本地运行优先，不暴露公网端口。
- 不向未授权第三方泄露客户产品信息、运营数据或平台账号凭证。
- 发布操作必须经过人工审核，不允许全自动黑箱发布。
- 日志中不得输出明文密钥、Cookie、账号密码或完整平台凭证。
- 数据库应支持本地备份，避免误操作造成不可恢复的数据损失。

## 失败行为

每个操作都必须产生可见结果，或者记录明确的非执行结果。

失败信息必须说明：

- 哪个操作失败
- 失败原因
- 数据是否受损
- 是否可以重试
- 操作者下一步应该做什么

禁止使用空提示、通用成功消息或静默重试掩盖失败。

## 测试规则

测试必须保护可观察行为或独立契约。

添加测试前必须回答：

1. 它保护什么行为或不变量？
2. 哪种可信的回归会触发它？
3. 现有测试为什么无法发现该问题？

优先为以下边界编写测试：

- 客户 CRUD 和客户状态流转。
- 产品画像生成结果的结构化校验。
- 运营策略和排期生成的字段完整性。
- 内容状态流转：待生成、已生成、待审核、已通过、已拒绝、已发布。
- 审核操作权限与状态限制。
- 发布适配器接口契约和失败重试。
- 平台凭证加密、脱敏展示和日志保护。
- 内容效果数据录入和报表统计。
- 日期、时区和定时发布处理。
- 表单校验和 API 错误展示。

回归测试必须在修复前因为预期原因失败。
禁止通过降低断言强度来获得通过。

## 验证顺序

优先执行与修改范围匹配的最小验证：

1. 后端聚焦单元测试。
2. 前端类型检查（`tsc --noEmit` 或项目等价命令）。
3. Lint。
4. 构建。
5. 端到端手动验证：M1 至少覆盖“客户创建 → 产品画像 → 策略 → 排期 → 内容生成 → 审核 → 复制/导出”中的相关切片；后续阶段再覆盖发布记录和数据追踪。

每次修改后，必须报告实际执行的命令和结果。
只完成静态检查时，不得声称功能已经完整可用。
